# API-контракт family-tree

Этот файл — согласованный контракт между бэкендом (Java Spring, пишет пользователь)
и фронтендом (Vue 3 + TS, пишет Claude). Меняется по согласованию обеих сторон;
именно этот файл — источник истины для URL, а не код.

Авторизация — JWT (см. "Аутентификация" ниже). Дерево не привязано к одному
владельцу: `Tree` — самостоятельная сущность, доступ к ней выдаётся отдельно
через `UserFamilyTree` (сейчас без градации прав — есть строка доступа
означает полный доступ; уровни доступа — решение на потом).

## Модель данных

> **Открытый вопрос:** таблицы ниже (кроме User/Tree/UserFamilyTree) описаны с
> `id: UUID`, а реально построенные сущности бэкенда (`User`, `Tree`,
> `UserFamilyTree`) используют `Long`, каждая — со своей собственной Postgres
> sequence (`users_id_seq`, `family_tree_id_seq`, `user_family_tree_id_seq`) —
> так исторически сложилось, когда auth писался раньше, чем
> Person/Relationship/Photo. Person/Relationship/Photo пока не реализованы в
> бэкенде: когда дойдёт очередь, стоит явно решить — тоже `Long` (единообразно
> с остальными таблицами) или всё же `UUID` (иногда предпочтительнее для
> сущностей, которые могут когда-нибудь синхронизироваться между разными
> базами/клиентами) — и обновить этот файл и фронтенд-типы соответственно,
> а не оставлять расхождение молча.

Общие для `User`/`Tree`/`UserFamilyTree` поля (унаследованы от `AuditEntity` в
бэкенде): `createdAt`/`updatedAt` (`LocalDateTime`, всегда заполнены),
`createdBy`/`updatedBy` (string — email пользователя или `"system"` для
неаутентифицированных операций вроде саморегистрации) и `deletedAt`/
`deletedBy` (nullable — колонки для будущего soft-delete уже есть, но ничего
их пока не заполняет и не фильтрует по ним: `DELETE` — по-прежнему настоящий
`DELETE`). В БД у каждой из трёх таблиц эти поля называются с префиксом имени
таблицы (`users_created_at`, `family_tree_created_by`,
`user_family_tree_deleted_at` и т.д.) — колонки в таблицах ниже показывают
только "логическое" имя поля, без этого префикса.

### Relationship
| Поле | Тип | Описание |
|---|---|---|
| id | UUID | |
| type | enum: PARENT_CHILD, SPOUSE, SIBLING | |
| personAId | UUID | Для PARENT_CHILD — родитель; для SPOUSE/SIBLING — один из пары |
| personBId | UUID | Для PARENT_CHILD — ребёнок; для SPOUSE/SIBLING — второй из пары |
| marriageDate | date | Только для SPOUSE, опционально |
| divorceDate | date | Только для SPOUSE, опционально |
| status | enum: MARRIED, DIVORCED, WIDOWED, PARTNERSHIP | Только для SPOUSE |

SIBLING хранится явной связью, а не только выводится из общих родителей: это
позволяет отметить "брат/сестра", даже когда общие родители ещё не внесены в
дерево или неизвестны. Когда родители всё же добавлены и это делает SIBLING
избыточной, объединять/удалять дубликат — забота бэкенда при создании связи
(валидация на дубли), не фронтенда.

## Аутентификация

JWT в заголовке `Authorization: Bearer <token>`. Все `/api/**`, кроме
`/api/auth/**`, требуют валидный токен — без него или с невалидным сервер
отвечает `401 { "error": "UNAUTHENTICATED", ... }`. Токен несёт `userId` в
`sub`; срок жизни задаётся на бэкенде (`app.jwt.expiration-minutes` в
`application.yml`), сейчас — без refresh-токена, по истечении нужно логиниться
заново.

| Метод | URL | Описание |
|---|---|---|
| POST | `/api/auth/register` | `{ email, password, displayName }` → создаёт пользователя (пароль хэшируется bcrypt), возвращает токен + профиль |
| POST | `/api/auth/login` | `{ email, password }` → возвращает токен + профиль либо `401 INVALID_CREDENTIALS` |

Ответ обоих: `{ token, expiresInSeconds, userId, email, displayName }`.

Списка деревьев пользователя (`GET /api/trees` или похожий) в контракте пока
нет — `UserFamilyTree` в бэкенде уже есть, но эндпоинт для чтения списка
доступных деревьев ещё не спроектирован; фронтенд соответственно тоже пока не
умеет показывать больше одного дерева (см. CLAUDE.md).

## Эндпоинты

Базовый путь: `/api`. Формат: JSON, `Content-Type: application/json` (кроме загрузки фото).

### Persons

| Метод | URL | Описание |
|---|---|---|
| GET | `/api/persons?search=&page=&size=` | Список персон, постраничный поиск по имени/фамилии |
| GET | `/api/persons/{id}` | Карточка одной персоны |
| POST | `/api/persons` | Создать персону |
| PUT | `/api/persons/{id}` | Обновить персону |
| DELETE | `/api/persons/{id}` | Удалить персону (и все её связи) |
| GET | `/api/persons/{id}/relatives` | Прямые родственники: родители, дети, супруги, братья/сёстры — для панели деталей |

### Photos

| Метод | URL | Описание |
|---|---|---|
| GET | `/api/persons/{id}/photos` | Галерея — все фото, где отмечен этот человек |
| POST | `/api/photos` | Загрузить фото (multipart/form-data: файл + `personIds[]` + опц. `caption`, `takenDate`) |
| PUT | `/api/photos/{id}` | Обновить подпись/дату/список отмеченных людей |
| DELETE | `/api/photos/{id}` | Удалить фото целиком |
| POST | `/api/persons/{id}/photos/{photoId}/untag` | Снять метку этого человека с фото (не удаляя фото, если на нём есть другие) |
| PUT | `/api/persons/{id}/primary-photo` | Установить главное фото узла — тело `{ "photoId": ... }`, id должен быть из галереи этого человека |

### Relationships

| Метод | URL | Описание |
|---|---|---|
| GET | `/api/relationships?personId=` | Связи, в которых участвует персона |
| POST | `/api/relationships` | Создать связь |
| PUT | `/api/relationships/{id}` | Обновить связь (даты, статус) |
| DELETE | `/api/relationships/{id}` | Удалить связь |

### Граф дерева (для рендеринга)

| Метод | URL | Описание |
|---|---|---|
| GET | `/api/tree` | Весь граф `{ nodes: TreeNode[], edges: Relationship[] }` — для небольших деревьев |
| GET | `/api/tree/{personId}?up=&down=` | Подграф вокруг персоны: `up` поколений предков, `down` поколений потомков — для больших деревьев / ленивой подгрузки |

`TreeNode` — облегчённая проекция `Person` для отрисовки на графе, **не** полная
карточка: `{ id, firstName, lastName, middleName, gender, birthDate, deathDate, thumbnailUrl }`.
`gender` включён (а не только в полной карточке) потому что фронтенд красит
узел по полу и упорядочивает пары мужчина/женщина уже на уровне графа, без
похода за полной карточкой.
Полная карточка (`notes`, места, полный список фото) запрашивается отдельно —
`GET /api/persons/{id}` — только когда открывается окно редактирования конкретного
человека. Это и есть механизм "не перегружать систему": граф целиком передаёт
только то, что нужно для подписи узла, а `thumbnailUrl` — это просто URL-строка;
сам файл фотографии браузер подгружает лениво и только для узлов, которые
компонент дерева реально отрисовал с фото (см. заметку о зуме в CLAUDE.md).

## Ошибки

Единый формат ошибки (рекомендация):
```json
{ "error": "PERSON_NOT_FOUND", "message": "Person a1b2... not found" }
```
HTTP-коды: 400 (валидация), 404 (не найдено), 409 (конфликт, напр. удаление персоны
с существующими связями без каскада), 500.

## Возможное развитие (не в стартовой версии)

- Уровни доступа в `UserFamilyTree` (сейчас — только «есть строка = полный доступ»).
- Эндпоинт(ы) для списка/создания деревьев пользователя (`GET/POST /api/trees`).
- Refresh-токены (сейчас JWT только с фиксированным TTL, без обновления).
- Импорт/экспорт GEDCOM (`/api/export/gedcom`, `/api/import/gedcom`).
